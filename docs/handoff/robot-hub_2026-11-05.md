## WP1 - Person tags

**Files:** `app/services/person_tags.py` (new: rules, parse, merge, lookup),
`app/migrations/015_person_tags.py` (new), `app/models/models.py` (`Person.tags`, JSON),
`app/api/people.py` (out field, `?tag=`, `tags` form field on create/update),
`app/services/person_address.py` (`address_for` returns tags), `app/services/look_service.py`,
`app/api/history.py`, `app/api/recognition.py` + `app/api/nodes.py` (events feed).

**Rules:** list of 1-32 character tags (letters of any script, digits, `-`, `_`, `.`), trimmed,
lowercased, de-duplicated, at most 20; default `[]`.

**API (all additive):**
- `GET /api/people`, `GET /api/people/{id}`: `"tags": ["vip","staff"]`. `GET /api/people?tag=vip`
  (bare list or `&page=1`) filters by a whole tag; an invalid `tag` is 422.
- `POST /api/people` and `PUT /api/people/{id}` (multipart, existing forms): optional
  `tags=vip,staff` or `tags=["vip","staff"]`. On PUT a left-out field keeps the tags; `tags=` clears.
  Invalid -> 422, nothing changes.
- `/api/look` face: `"tags": ["vip","staff"]` for a matched person, `"tags": []` for unknown.
- Events feed message: `{"node_id":"MOBILE-01","participant_id":"9001",…,"call_as":"พี่แอน","tags":["vip"]}`.
- `/api/history` item: `"tags": [...]` (the person's current tags; `[]` for unknown).

**Migration 015:** `person.tags JSON NOT NULL DEFAULT '[]'`; existing people get `[]`. Runs
automatically at startup (`init_db`), idempotent. Rollback: revert the code; the column is ignored
by older code (never dropped).

**Tests:** TagRulesTests (3), Migration015Tests, TagsApiTests (create/update/filter/read; look,
history, feed for kiosk-central and local-agent paths), IdStabilityTests. Existing exact-key
assertions were widened by `tags` only (test_robot_contract, test_look_api,
test_inference_api_contract, test_robot_history, test_presence, test_recognition_persist).

## WP2 - Import tags

**Files:** `app/migrations/016_import_tags.py` (new), `app/models/models.py`
(`ImportRow.tags`, `ImportRow.tag_errors`, `ImportJob.tags_mode`), `app/services/import_service.py`
(`detect_tags_column`, `parse_tags_cell`, `attach_tags`, `_apply_row_tags`, `run_import_job`),
`app/api/imports.py` (both previews + confirm).

**Behaviour:** optional column headed `Tags` or `Tag`; values separated by `,` or `;`.
New people get the valid tags. Existing people — reached only by the Google Sheet sync, exactly like
PDPA consent (a file upload never changes an existing participant) — get them **merged** (default) or
**replaced** (`tags_mode=replace` on confirm). No Tags column -> nobody's tags change. Invalid values
are skipped and reported; the import never fails because of them.

**API (additive):**
- Preview (`POST /api/import/preview`, `POST /api/import/sheet/preview`): `"tags_column": "Tags"`
  (or null), `"invalid_tag_rows": 1`, and per row `"tags": ["vip"]` (null when no column),
  `"invalid_tags": ["bad tag"]`.
- `POST /api/import/{id}/confirm`: new form field `tags_mode` = `merge` (default) | `replace`; other -> 422.
- `GET /api/imports/{id}`: rows carry `tags` and `tag_errors`; the job carries `tags_mode`.

**Migration 016:** `importrow.tags JSON NULL`, `importrow.tag_errors VARCHAR NULL`,
`importjob.tags_mode VARCHAR NOT NULL DEFAULT 'merge'`. Automatic, idempotent; rollback = revert code.

**Tests:** TagImportTests — file with the column (valid + bad values, job completes, errors per
row), file without the column (unchanged behaviour), bad `tags_mode`, sheet sync merge / replace /
no column / blank cell.

## WP3 - Capacity hints + 429 body

**Files:** `app/services/live_scheduler.py` (active-source tracking, per-frame time, `capacity()`),
`app/services/look_service.py` (`LookError.limit/reason/retry_after_ms`, in-flight counter),
`app/services/health_status.py` (`look_capacity`), `app/api/look.py` (`LookBusy`), `app/main.py`
(429 handler).

**`GET /api/health` (additive):**
```json
"look_capacity":{"max_live_fps":24.6,"frame_ms":40.6,"active_sources":6,"active_window_s":10.0,
  "headroom":0.8,"recommended_fps_per_source":3.3,"inflight_turn":1,"queue":2,"queue_limit":64,
  "per_source_waiting_max":1,"per_source_waiting_limit":1,"inflight":3,"inflight_limit":12,
  "frame_deadline_ms":500,"max_batch":8}
```
`max_live_fps` = 1000 / measured live model time per frame (null before the first frame);
`recommended_fps_per_source` = 80% of it / sources active in the last 10 s. In memory only
(health measured < 0.5 s in tests; no inference, no DB).

**429 body (additive; detail text and Retry-After / X-Retry-After-Ms headers unchanged):**
```json
{"detail":"This source already has a frame waiting; drop this one. (live queue)",
 "limit":"per_source","reason":"source_busy","retry_after_ms":120}
```
`limit` per_source | global_queue | timeout; `reason` source_busy | queue_full | inflight_full |
turn_timeout | model_busy.

**Tests:** CapacityTests, BusyBodyTests (global_queue/inflight_full over HTTP incl. headers;
per_source and timeout; health fields and speed). Docs explain how a client throttles itself.

## WP4 - Batch look

**Files:** `app/face_recognition/engine.py` (`detect_faces_batch`), `app/services/look_service.py`
(`look_batch`), `app/api/look.py` (`POST /api/look/batch`), `app/main.py` (body cap for the new path).
`POST /api/look` is unchanged apart from the additive `threshold_used` / `tags` fields.

**API:** multipart `photos` (1-8 JPEGs) + optional `sources` (one per photo, same order).
```json
{"took_ms":180.4,"kept":false,"items":[
 {"index":0,"source":"cam-1","status":200,"image":{"w":640,"h":480},"took_ms":180.4,"kept":false,
  "threshold_used":0.45,"faces":[{"box":[…],"status":"matched","participant_id":"9002",…,"tags":["vip"]}]},
 {"index":1,"source":"cam-2","status":400,"detail":"Photo is not a JPEG."},
 {"index":2,"source":"cam-3","status":429,"detail":"…","limit":"global_queue","reason":"inflight_full","retry_after_ms":200}]}
```
Whole request 429 only if every item was refused as busy; 422 for 0 or >8 photos or a wrong-length
`sources`. Machine account allowed.

**GPU batching:** the installed detector (`det_10g.onnx`) has a fixed batch size of 1, so frames
are detected one after another inside one live turn; the recognition model (`w600k_r50.onnx`,
dynamic batch) embeds **all faces from all frames in one call**. Embeddings are identical to
`/api/look` (real model: min cosine 1.0 over 12 faces).

**Benchmark** (RTX 4050 Laptop 6 GB, CUDA, dual mode, in-process harness — no HTTP; 8 cameras x
4 fps = 32 fps offered, which exceeds this GPU; 40 s per run, interleaved, 2 rounds; NOT comparable
with the RTX 5070 Ti numbers):

| run | answered fps | p50 ms | p95 ms | p99 ms | 429 | longest 429 run | VRAM max |
|---|---|---|---|---|---|---|---|
| single, before (e8d4a22 code) r1 / r2 | 23.5 / 26.9 | 322 / 296 | 426 / 348 | 525 / 361 | 6 / 0 | 0.54 / 0 s | 951 / 945 MB |
| single, after r1 / r2 | 25.9 / 26.3 | 300 / 299 | 374 / 359 | 465 / 379 | 2 / 0 | 0.51 / 0 s | 947 / 951 MB |
| batch of 8, after r1 / r2 | 22.9 / 20.2 | 312 / 365 | 569 / 640 | 627 / 713 | 0 / 0 | 0 / 0 s | 1087 / 1117 MB |

Reading: the single `/api/look` path is unchanged within run-to-run noise (latency and VRAM did
not get worse). The batch removes 429s but is **slower** here (lower throughput, higher p95, ~150 MB
more VRAM for larger recognition batches): detection, the dominant cost, cannot be batched with the
installed detector, and one batch in flight leaves the GPU idle while the next batch is decoded and
answered. Recommendation: keep single `/api/look` for the hub on this kind of GPU; re-measure on
the RTX 5070 Ti with `tools/look_batch_bench.py` before switching.

## Decisions / known limits

- Tags are stored as a JSON list on the person (no separate table); the `?tag=` filter is a text
  match on the normalised list, fine for hundreds to a few thousand people.
- `PUT /api/people/{id}` keeps tags when the field is left out (unlike the other fields of that
  full-form PUT) so existing clients and the admin UI never wipe them.
- History items show the person's **current** tags, not the tags at detection time.
- Tag import updates existing people only through the Sheet sync (same rule as consent); file
  uploads tag new people only. Default merge; replace with a blank cell clears.
- No admin UI for tags or per-camera thresholds yet (API only); the Settings page round-trips the
  new key unchanged.
- `max_live_fps` measures the live model only; decoding, the network and (in shared mode) background
  work lower what is really achievable. A batch counts as one fair-share turn for its account.
- Per-camera thresholds apply to `/api/look`, the batch and central camera nodes; Local-Agent CCTV
  nodes match on the station PC and are not affected.
- WP7 (webhook) not started.
